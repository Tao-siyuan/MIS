# 专业设置及排课管理系统（MIS）

面向北京科技大学本科教学运行管理，覆盖 **“专业设置—课程设置—排课—课表服务”** 全流程，
并延伸支持辅修/二学位、转专业学分转换、课程评价、角色权限与操作日志审计。

系统完全依据《系统分析、设计、规划报告》中的系统规划、数据字典（2.2）、数据库设计（3.4）、
处理过程设计（3.5）与输入输出设计（3.6）实现。

---

## 一、技术栈

| 层次 | 技术 | 说明 |
| --- | --- | --- |
| 前端 | Vue 3 + Vite + Element Plus | 单页应用，Axios 以 RESTful JSON 访问后端 |
| 后端 | Java 17 + Spring Boot 3.2 | Controller—Service—Mapper 三层，业务规则集中在 Service |
| 持久层 | MyBatis-Plus 3.5.7 | 条件构造器 + 自定义联表查询（ViewMapper） |
| 数据库 | MySQL 8.0（InnoDB / utf8mb4） | 22 张业务表 + 1 个完整课表视图 |
| 认证 | JWT + 拦截器 + RBAC | 令牌校验、功能权限码、数据范围（全校/本学院/本人） |

## 三、快速启动

### 1. 初始化数据库

```bash
mysql -uroot -p < docs/database.sql
```

脚本会重建 `mis` 库（含 20 个学院、15 个专业、40 门课程、14 个教学班、13 段排课、
4 份培养方案、6 类角色与 8 个演示账号）。

### 2. 启动后端（端口 8081）

```bash
cd backend
mvn spring-boot:run
```

数据库连接配置见 `backend/src/main/resources/application.yml`：

```yaml
username: root
password: tsy050904
```

### 3. 启动前端（端口 5173）

```bash
cd frontend
npm install
npm run dev
```

浏览器访问 <http://localhost:5173>。

## 五、数据库设计要点

### 5.1 表清单（共 22 张业务表 + 1 视图）

基础档案：`college`、`major`、`course`、`class_info`、`teacher`
培养方案：`major_program`、`program_course`、`general_plan`
课程与任务：`new_course_apply`、`teaching_class`
排课：`classroom`、`schedule_rule`、`schedule_result`、`schedule_conflict`、`adjust_record`
延伸业务：`dual_enroll`、`study_record`、`credit_apply`、`credit_item`
评价监督：`eval_plan`、`eval_record`、`sys_role`、`sys_user`、`sys_user_role`、`audit_log`
视图：`v_full_schedule`（课表唯一出口，仅展示已发布/已调课记录）

### 5.2 关键约束

- 组合主键：`major_program(专业, 年级, 方案类型)`、`program_course(+课程号)`、
  `general_plan(学年, 课程号)`、`credit_item(申请编号, 明细序号)`
- 唯一约束：课程名称、学院名称、角色名称、评教记录 `(方案, 教学班, 学号)`
- 外键：全部业务外键均建立，方案删除级联删除明细，排课删除级联删除冲突记录
- 受控冗余：`schedule_result.week_range` 以区间存储；`credit_apply.apply_credit` 由明细汇总回写；
  `eval_record.score` 由分项按权重折算

## 六、业务规则实现

| 编号 | 规则 | 实现位置 |
| --- | --- | --- |
| BR-01 | 培养方案毕业总学分区间校验（主修 100~200，双学位 40~80） | `ProgramService.save` |
| BR-02 | 同一课程在同一方案只能列入一次；先修课程须在前一学期或更早 | `ProgramService.addCourse` |
| BR-03 | 方案课程为空或学分合计不达标不得提交评审 | `ProgramService.submit` |
| BR-04 | 教学班容量上限不得小于面向班级人数 | `TeachingClassService.save` |
| BR-05 | 存在未处理排课冲突时不允许发布课表 | `ScheduleService.publish` |
| BR-06 | 已发布方案不得修改课程明细，已引用课程只能改大纲与考核方式 | `ProgramService` / `CourseController` |
| BR-07 | 存在未确认跨院课程时不得提交评审 | `ProgramService.submit` |
| BR-08 | 存在进行中教学班的课程不得停开 | `CourseController.changeStatus` |
| BR-09 | 认定学分不得超过替代课程学分 | `DualController` / `CreditController` |
| BR-10 | 学生同一学年只能报名一个双学位专业，录取受名额限制 | `DualController.enroll` |
| BR-11 | 评教窗口外不能提交，同一学生对同一教学班只能提交一次 | `EvalService.submit` |

## 七、排课算法说明

采用 **“贪心初排 + 冲突记录 + 人工微调”**，不追求全局最优：

1. **需求计算**：每周段数 = 计划学时 ÷ 上课周数 ÷ 2（四舍五入，至少 1 段）。
2. **候选排序**：公共基础课（校级必修/通识）优先上午节次；其余课程优先靠后节次；
   教师偏好节次前置。
3. **硬约束校验**：教师不冲突、教室不冲突、面向班级不冲突、教室容量 ≥ 面向人数、
   教室类型与教学形式匹配、不占用教师不可用时间。
4. **教室选择**：同类型教室按容量升序（最佳匹配）。
5. **未分配处理**：写入 `schedule_conflict`（冲突类型 + 描述 + 建议方案），
   由教务员在工作台采纳建议或人工指定时段后重新校验。
6. **发布**：校验无未处理冲突 → 批量置为已发布并锁定 → 写入操作日志并刷新课表视图。

## 八、权限设计

- **功能权限**：24 个权限码（P01~P24），由 `@RequirePerm` 注解在接口上声明，
  拦截器按角色 `func_perm` 校验，越权返回 403。查询与审批权限严格分离：

  | 权限码 | 含义 | 授予角色 |
  | --- | --- | --- |
  | P01~P05 | 学院专业、方案编制、方案审核发布、通识计划、课程库 | R01/R02（P02 另授 R03） |
  | P06 / P21 / P07 | 新增课程申报 / 学院初审 / 教务处终审 | R04 / R03 / R02 |
  | P08 / P19 | 教学班查询 / 教学班维护 | 全员查询，维护仅 R01/R02/R03 |
  | P09~P11 | 排课发布、调课申请、调课审批 | R02 / R04 / R02 |
  | P12~P15 | 课表查询、双学位报名、学分转换、评教提交 | 按角色 |
  | P13 / P17 | 双学位报名查询 / 双学位录取审批 | 学生/R03 查询，审批仅 R01/R02 |
  | P15 / P18 | 评教提交查询 / 评教方案管理 | 全员提交，方案管理仅 R01/R02 |
  | P16 / P20 | 操作日志审计 / 角色与用户配置 | 审计 R01/R02/R06，配置仅 R01 |
  | P22 / P23 | 跨院课程确认 / 通识课程承接确认 | R02/R03 |
  | P14 / P24 | 学分转换申请 / 学分认定审核 | 学生申请，审核仅 R01/R02/R03 |

- **数据权限**：`data_scope` 为 1 全校 / 2 本学院 / 3 本人，列表查询自动追加过滤条件
  （教师看本人教学班与评教统计、学生看本班已批准调课与本人数据、学院教务员看本学院数据）。
- **多角色**：`sys_user_role` 为权限来源，权限取并集、数据范围取最宽，`sys_user.role_id` 仅表示主角色。
- **操作留痕**：登录（07）与登出（08）同样写审计；方案发布、排课发布、调课审批、学分认定、
  授权变更等关键写操作均记录操作人、角色、类型、对象、变更前后值、IP 与时间，日志只追加不修改。

## 九、说明

1. 按“一数一源”原则，班级、教师、教室数据分别由学籍、师资、固定资产子系统维护，
   本系统仅保存镜像表并只读引用；演示环境内置了镜像数据以保证系统可独立运行。
2. 专业编号长度放宽至 8 位，以容纳国家特设专业代码（如 `080717T`）。
3. 文件服务（课程大纲、导出报表）在演示环境以路径字段占位，接口形态与设计文档一致。
4. 前端 `npm run build` 产物位于 `frontend/dist`，可交由 Nginx 托管并将 `/api` 反向代理至后端。
5. 登录账号即人事工号 / 学籍学号；`teacher.teacher_id` 沿用师资子系统编号（如 `T2026001`），
   由 `sys_user.teacher_id` 关联，与登录工号分属两套标识。
6. 口令以 `SHA-256("mis@" + 明文)` 摘要存储（`AuthService.hash`）；管理员重置密码时留空即按口令规则生成。
7. 培养方案版本化：方案主表只保留当前版本，历史版本归档到 `major_program_version`（只读）；
   方案状态机为 0 编制中 → 1 院系初审 → 2 教务处审核 → 3 已发布，仅 0 状态可编辑课程明细。
8. 会话保存在 `sessionStorage`，每个浏览器标签页独立登录，可在多个标签页同时使用不同账号；
   关闭标签页即失效，切换账号不会影响其他标签页。
9. 课表导出为 `.xlsx`（`xlsx` 依赖按需加载）：第一个工作表与页面周课表网格一致，
   第二个工作表为课程明细；导出行为写入操作日志（类型 06）。
10. 学分转换只允许“原专业课程 → 转入专业课程”的单向认定：原修课程须在原专业方案中、
    认定课程须在转入专业方案中，且同一原课程不得重复认定；审核需 `P24` 权限。
11. 课程性质共 7 类：11 校级必修 / 12 院级必修 / 13 专业必修 / 14 专业选修 / 15 通识 /
    16 实践教学 / 17 素质拓展。
12. 教师与学生工作台以个人信息卡（姓名、学号/工号、学院、专业、班级、职称）替代统计指标，
    并在下方展示“今日日程”；教务与管理员仍展示运行指标与最近操作。
13. 课表查询中教师仅能查看本人课表（前端隐藏其他视图，后端对 `view/key` 二次校验）；
    教师不参与学生评教，只能在评教结束（方案状态 2）后查看教务处反馈的汇总结果，学生原始评价记录不对教师开放。
14. 调课申请选择新时间后，系统仅列出该时段可用且满足教学形式与人数要求的教室，
    并提示同一时段该班级学生已有课程冲突的涉及人数与明细。
15. 师资编号（`teacher.teacher_id`，如 `T2026001`）不对外展示，凡涉及教师的界面与下拉均统一显示登录工号
    （`sys_user.user_id`，如 `A230001`）；工作台个人信息卡只展示职称，不再显示所属系。
16. 教学班学生名单落库于 `tc_student`（`tc_id + stu_id` 主键）：任课教师可在本人教学班内按“学号 + 姓名”
    添加学生（学号自动带出姓名供核对，学号与姓名不一致时报错），教务处与学院教务员按数据范围维护；
    添加时校验学生身份（`R05`）、去重与容量上限，并回写 `actual_num`。
17. 调课申请支持撤回：仅待审批（`approve_status=0`）的申请可由申请人（本人教学班教师）或具备 `P11` 权限的角色撤回，
    撤回后状态置为 3 已撤回，不修改课表；已批准的调课仍走“撤销调课”按快照恢复。
18. 新增课程申报按角色限定课程性质：教师仅可申报 17 素质拓展；学院教务仅可申报 13 专业必修 / 14 专业选修，
    自报课程直接进入教务处待审；教务处仅可申报 15 通识，须指定下发学院，申报状态置为 4 待学院补充，
    由下发学院教务补充学分/学时/开设理由后转 3 教务处待审。
19. 学院教务在申报列表可见本学院教师的申报与下发到本学院的通识课程（`new_course_apply.apply_user` 存登录工号），
    并仅能初审本学院（或下发本学院）的申报；驳回须填写理由。
20. 调课为两级审核：学院教务（`P21`）初审 0 → 4 待教务处备案（驳回置 2），教务处（`P11`）备案 4 → 1 生效并按新安排更新课表；
    学院教务只能审核本学院开课课程的调课申请。
21. 课表查询中学院教务（数据范围 2）仅可查看本学院班级课表（按班级所属专业的学院校验）与本学院开课课程的课表：
    教师视图须为本学院教师，教室视图仅返回本学院开课课程，跨学院查询返回 403。
22. `teacher.teacher_id`（师资子系统编号）仅内部关联使用，界面一律展示登录工号；基础数据接口对学院教务自动收敛到本学院班级与教师。
